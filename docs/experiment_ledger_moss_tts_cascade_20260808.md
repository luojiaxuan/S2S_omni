## 0. 一句话现状

v3 + session-reset 仍是操作点（ACL6060 En-Zh，GPT-ASR 口径 BLEU 34.69）。
**v4 scheduled sampling 的判决在 GPT-ASR 复测后被推翻**：它在滑窗模式下
**+5.61 BLEU**（18.53 → 24.14），在 reset 模式下 **−2.18 BLEU**——是一次
真实的取舍，不是无效。我此前"v4 无增益"的结论是**测量仪器造成的假象**：
Qwen3-ASR 会折叠重复，把 v4 修好的东西一并抹平（同一对在 Qwen3 下是
22.26 vs 22.38 持平）。详见 6.3。下一个决策点见第 7 节。

## 1. 三十秒背景

**在回答什么**：能否用「InfiniSST（en→zh 流式语音翻译）→ MOSS-TTS-Realtime
（中文流式 TTS）」这条级联，在 ACL6060 长演讲同传任务上追平 GPT-realtime /
Gemini-live / KIT 这类端到端商用系统。

**为什么值得答**：级联可控、可分别优化、可自托管；若能追平，说明不必依赖
闭源端到端模型。

**成功长什么样**：ACL6060 En-Zh，SEGALE canonical 协议下的 BLEU / XCOMET-XL
进入商用系统档位（GPT 32.70 / Gemini 40.39 / KIT 34.76，均 GPT-ASR 口径），
且整场 talk 不崩、null（漏译）率与它们相当（约 8%）。

**现状**：v3 + reset 达到 BLEU 34.69 / XCOMET 0.554 / null 6.8%，已越过
GPT、贴平 KIT，未及 Gemini。

## 4. 实验台账（时间倒序）

### 4.0 韵律锚点：1 秒 carry 也不行（2026-08-08 晚，用户批准）

- **假设**（我提出的）：4.1 证明保留整轮历史要付 6–8 BLEU，但如果只 carry
  上一段结尾**约 1 秒**的 codes 当韵律锚点，长度不足以让一个音频循环重新
  自我强化，应该能既接住音色语调、又不重开污染通道。
- **改动**：`moss_multiturn_infer.py` 新增 `--reset-carry-seconds`
  （commit `444f002`）；只留尾部 N 秒 codes，文本按帧数比例截同样长度的
  尾巴；runaway/失败的行不传递锚点。
- **现象**（v3ctl checkpoint，**GPT-ASR**，5 talks）：

  | 边界携带 | BLEU | XCOMET | null |
  | --- | ---: | ---: | ---: |
  | 0（硬切 reset） | **34.25** | 0.535 | 7.2% |
  | **1 秒 codes** | **30.91** | 0.477 | 14.8% |
  | 5 轮（≈"保留一半"） | 约 20（Qwen3 19.90，GPT 未测，预期更低） | 0.372 | 18.1% |
  | 10 轮（滑窗 w=11） | 18.53 | 0.315 | 21.1% |

- **判断**：**我的推测被证伪。** 1 秒 carry 就要付 **−3.34 BLEU**，null 率
  翻倍（7.2% → 14.8%）。而且把四个点连起来看，**质量随携带量单调下降，
  不存在"安全的小剂量"阈值**——任何跨边界的声学携带都在重开污染通道。
- **去留**：**不采纳任何形式的边界携带，保持硬切。** 若要修韵律断点，
  必须走**不经过模型上下文**的路子：波形级 crossfade（事后处理，零内容
  风险），或数据侧让模型学会"平滑开场"（在训练里构造承接前段韵律的
  session-start 样本），而不是在推理时把上一段喂回去。

### 4.1 滑窗窗口扫描：回答"reset 不硬切、保留一半历史"（2026-08-08）

- **假设**：如果滑窗掉分的原因是"历史太长/太脏"，那么缩短窗口应该改善；
  如果原因是"从不清零"，那么**在相同平均历史长度下**，会清零的 reset 应该
  显著优于不清零的滑窗。这两个假设可以用 sliding6 vs reset11 直接区分——
  两者平均历史长度都约 5 轮，唯一差别是 reset 周期性清零。
- **现象**（v3ctl checkpoint，Qwen3-ASR，5 talks）：

  | 配置 | 历史长度 | 是否清零 | BLEU | XCOMET | null |
  | --- | --- | --- | ---: | ---: | ---: |
  | 滑窗 w=11 | 恒 10 轮 | 否 | 22.38 | 0.401 | 5.9% |
  | 滑窗 w=6 | 恒 5 轮 | 否 | **19.90** | 0.372 | 18.1% |
  | 滑窗 w=3 | 恒 2 轮 | 否 | 21.60 | 0.362 | 24.9% |
  | reset 每 11 轮 | 平均约 5 轮 | **是** | **28.14** | 0.503 | 16.6% |

- **判断**（已证实部分）：**决定性因素是"是否清零"，不是历史长度。**
  三个不清零的滑窗变体 BLEU 落在 19.90–22.38 的窄带内，带宽（2.5）与实测
  run 方差（1.6，见 6.1）同量级，**彼此统计上不可区分**；而清零的 reset
  是 28.14，高出整个窄带 **约 6–8 BLEU**。特别地 sliding6 与 reset11 平均
  历史长度相同（约 5 轮），差 8.24 BLEU，把"长度"这个解释排除干净。
  在不清零的前提下，历史越短，XCOMET 与 null 率单调恶化
  （0.401→0.372→0.362，5.9%→18.1%→24.9%），只是 BLEU 被噪声淹没。
- **改动**：`scripts/acl_cascade_eval/run_eval_queue.sh` 支持 `slidingN` 模式。
- **结果**：见上表。
- **去留**：**保留 reset 硬切**。"保留一半历史"属于不清零变体，预期落在
  19.9–22.4 这个窄带里，比现操作点（28.14）差约 6–8 分，不采纳。若目标是修复韵律断点，
  应走不重开污染通道的路子（建议见第 7 节）。

### 4.2 v4 scheduled sampling 第一阶段（2026-08-08）

- **假设**：v3 滑窗仍差于 reset，是因为训练时的历史是 base 模型一次性合成
  的干净切片（开环），而推理时是模型自产（闭环）——即 exposure bias。若用
  模型自己的闭环输出替换训练上下文，滑窗应显著改善（预设判据：滑窗 BLEU
  从 16.41 推到 25+ 才继续第二阶段）。
- **现象**：

  | | 滑窗 w=11 | reset 11 轮 |
  | --- | --- | --- |
  | v4（自生成历史） | 22.26 / 0.406 / null 7.8% | 29.03 / 0.551 / null 3.8% |
  | v3ctl（手写污染，对照） | 22.38 / 0.401 / null 5.9% | 28.14 / 0.503 / null 16.6% |

  ASR 转写 8-gram 重复率：v3ctl 滑窗 **0.070** → v4 滑窗 **0.013**
  （reset 各版本均为 0.013–0.016）。
- **判断**：
  - **已证实**：v4 把滑窗的音频循环压低 5.4 倍，降到与 reset 同一水平。
    自生成历史训练在它的直接目标上是成功的。
  - **已证伪**：循环不是滑窗掉分的主因。去掉循环后 BLEU 纹丝不动
    （22.26 vs 22.38），**说明我原先的因果归因错了**。
  - **推测**（未证实）：剩余约 6 分更可能来自内容漏译/漂移而非重复——
    v4 滑窗 null 7.8% 是其 reset 的 3.8% 的两倍，且每秒信息量偏低
    （3.34 vs 3.53 字/秒）。需逐句 diff 才能定位。
- **改动**：新增 `scripts/gen_moss_self_history.py`（批量闭环自生成）与
  `scripts/build_moss_v4_dataset.py`（turn 级替换 + 漂移护栏），
  commit `3143faf`；v4 数据集 19,993 行（14,485 干净 + 5,508 自历史副本，
  21,641 个 turn 被替换）。
- **结果**：见上表。**在 Qwen3-ASR 口径下无增益。**
- **⚠️ 2026-08-08 晚：用户批准 GPT-ASR 复测后，本条判决被推翻。**
  canonical 口径（gpt-4o-mini-transcribe）下同样四个 run：

  | | 滑窗 w=11 | reset 11 轮 |
  | --- | --- | --- |
  | v4 | **24.14** / 0.386 / null 11.5% | 32.07 / 0.476 / null 17.4% |
  | v3ctl | 18.53 / 0.315 / null 21.1% | **34.25** / 0.535 / null 7.2% |
  | v3 原始 | 16.41 / 0.303 / null 21.8% | 34.69 / 0.554 / null 6.8% |

  **v4 在滑窗上 +5.61 BLEU、XCOMET +0.072、null 率从 21.1% 腰斩到 11.5%；
  在 reset 上 −2.18 BLEU、null 从 7.2% 恶化到 17.4%。** 两个方向都超过各自
  模式的 run 方差（reset 约 0.44、滑窗约 2.1，见 6.1 修订），所以
  **v4 是一次真实的取舍，不是无效**：它把模型调向"能在脏历史上稳住"，
  代价是干净上下文下的精度。
  与 8-gram 重复率的证据完全自洽——v4 确实消除了循环，而 GPT-ASR 会逐字
  转写循环（因此循环压 BLEU），Qwen3-ASR 会折叠循环（因此看不出差别）。
- **去留（修订）**：**操作点仍用 v3 + reset**（34.69 / 34.25 优于 v4 的
  32.07）。但**若产品需要真正的流式滑窗**（无边界断点），v4 是目前最好的
  滑窗模型（24.14，历史最佳）。第二阶段 DAgger 迭代**重新变得值得考虑**，
  但应只针对滑窗路线，且必须用 GPT-ASR 评测。

### 4.3 原生 MOSS baseline：量化 SFT 净收益（2026-08-08，用户要求）

- **假设**：需要一个"不做 SFT"的下界，才能知道整个微调工作值多少。
- **现象**（除 checkpoint 外全部逐字对齐 v3 操作点，Qwen3-ASR）：

  | | BLEU | XCOMET | null | 崩溃 session |
  | --- | ---: | ---: | ---: | ---: |
  | 原生 MOSS（无 SFT） | 23.14 | 0.246 | 31.9% | **46/160（28.8%）** |
  | v3 + reset | 29.75 | 0.556 | 5.6% | **0/160（0%）** |

- **判断**（已证实）：SFT 值 **+6.61 BLEU / +0.31 XCOMET**；更关键的是
  原生模型有 **28.8% 的会话直接 runaway 报废、无音频输出**，这是其 null 率
  31.9% 的主因。即原生模型在"多轮 assistant-only、每轮短文本、共享固定
  音色"这个形态下不具备稳定生成能力，而不只是质量差一点。
- **改动**：`acl_bench/score_base.py`、`run_base_queue.sh`。
- **结果**：见上表。**去留**：作为论文/汇报的下界基线保留。

### 4.4 v3：长会话 + 强污染训练（2026-08-05）

- **假设**：滑窗塌缩源于模型没见过"坏历史"，可用长会话拼接（20–35 turn）
  + 人工污染（轮内跳针 / 跨轮 carry / 整轮 replay，标 `context_only` 不进
  loss）提升鲁棒性。
- **现象**：v3 + reset 34.69 / 0.554 / null 6.8%（GPT-ASR），160 session
  零失败；v3 + 滑窗 16.41（GPT-ASR），比 v2 滑窗的 4.80 大幅回血但仍远低于
  reset。
- **判断**：长会话+污染同时修复了段内质量与 under-translation；reset 隔绝
  闭环反馈。**注意**：此处 34.69 vs 16.41 的 18.3 分差被我当作"滑窗代价"
  引用过多次，但 4.2 显示同 ASR 下该差距只有约 6 分——见 6.3。
- **改动**：`scripts/build_moss_v3_dataset.py`（commit `fb45fdb`）。
- **去留**：**保留为当前操作点。**

### 4.5 v2 滑窗塌缩与循环自强化（2026-08-05）

- **假设**：多轮增量推理应优于每段独立合成。
- **现象**：v2 滑窗 BLEU **4.80**、XCOMET 0.172、null 34%——完全塌缩；
  同 checkpoint 换 reset 则 23.96。
- **判断**（已证实）：滑动窗口内一旦出现音频循环，它成为下一轮上下文并
  自我放大，形成正反馈。文本侧的 repetition penalty 类手段失效，因为 RVQ
  codes 复述同一段声音时数值并不相同，n-gram 检测器不触发。
- **改动**：加入 `--loop-detect`、runaway 轮级跳过；最终改用 session reset。
- **去留**：reset 保留；滑窗留待 4.1/4.2 的后续研究。

### 4.6 v1 判死刑（2026-08-04，用户裁定）

- **假设**（原）：逐 segment 独立调 TTS 即可。
- **现象**：每段都是"静音起、静音止"的孤立朗读，拼接后断裂；用户直接判定
  "v1 在当前链路里可以宣告死刑"。
- **判断**：缺少跨轮连续性监督。**改动**：改为整行合成 + 强制对齐切片（v2）。
- **去留**：v1 弃用，仅保留记录。

### 4.7 0.96s chunk 档判无效（2026-08-05）

- **现象**：BLEU 6.86，talk268 假设 9,164 字符 vs 参考 3,532——重复翻译。
- **判断**：sglang client 在小增量 + 16/8 消息修剪下的续译语义与 RASST 原
  实现有偏差，被小 chunk 放大。**去留**：该档数字不进任何结论，待对拍修复。

## 6. 我犯过的错与纠正

### 6.1 用单 run 差异下结论（方法论错误，影响面最大）

- **错误**：v1→v2→v2.1→v3 的历次结论均基于单次训练 + 单次评测的差值。
- **如何发现**：这次用同一份 v3 数据、同一套超参在 Tilde 重训对照组，
  得到 BLEU 28.14 / null 16.6%，而原始 v3 是 29.75 / null 5.6%——
  **同配置重训的方差就有 1.6 BLEU，null 率从 5.6% 摆到 16.6%**。
- **纠正后**：v4 与对照组的差值（滑窗 0.12、reset 0.89 BLEU）**小于方差**，
  因此判定为"无可靠增益"而非"小幅提升"。
- **⚠️ 修订（GPT-ASR 复测后）**：那个 1.6 BLEU 的方差是在 **Qwen3-ASR**
  口径下测的，把 ASR 噪声也算进去了。同一对 checkpoint 在 **GPT-ASR** 下
  只差 **0.44 BLEU**（v3ctl reset 34.25 vs v3 原始 34.69）。所以：
  - **reset 模式下的训练方差约 0.44 BLEU**（canonical 口径）；
  - **滑窗模式下约 2.1 BLEU**（18.53 vs 16.41）——滑窗本身是不稳定区间，
    方差天然更大；
  - 之前那句"小于 1.5 BLEU 都不算数"对 Qwen3-ASR 数字成立，对 GPT-ASR
    数字过于保守。
- **已影响的结论**：历史上基于 **Qwen3-ASR** 的细粒度排序仍不可靠；基于
  GPT-ASR 的 reset 数字，0.5 分以上的差异可以认真对待。

### 6.2 LR 调度缺陷（沿用而非引入，但我此前未发现）

- **错误**：`sft.py` 计算 `num_training_steps` 时没有乘 `num_processes`，
  而 accelerate 每个 optimizer step 会把 scheduler 推进 `num_processes` 次，
  导致调度提前数倍跑完。
- **如何发现**：在 Tilde 上并排跑 5 进程与 3 进程两组时，发现两边 lr 差一个
  数量级。实证：5 进程 warmup 实际 8 步（= 0.03×1333/5）、lr 在 step
  306/1333 归零；3 进程 warmup 14 步（= 0.03×1390/3）。
- **纠正后**：**未在本次实验内修复**（会引入第二个变量），改为把两组都固定
  为 3 进程，让缺陷等价存在。
- **已影响的结论**：**v1/v2/v2.1/v3 全部是在"后约 2/3 训练 lr=0"的条件下
  训出来的**。修复它可能是一次免费的质量提升，但必须单独做对照。

### 6.3 用跨 ASR 的数字对比"滑窗代价"（归因错误）

- **错误**：多次引用"滑窗 16.41 vs reset 34.69，差 18.3 分"作为滑窗代价。
- **如何发现**：本次在同一 ASR（Qwen3）下测得 v3ctl 滑窗 22.38 vs reset
  28.14，差仅 5.8 分；v4 为 6.8 分。
- **纠正后**：**滑窗真实代价约 6 分，不是 18 分。** 差异的一部分来自 run
  方差，另一部分**疑似 Qwen3-ASR 会折叠重复**，使退化音频"看起来"没那么差。
- **⚠️ 已验证成立（2026-08-08 晚，用户批准约 $0.60 复测）**：
  **Qwen3-ASR 确实是评估滑窗退化的错误仪器。** 同一对 checkpoint：

  | 口径 | v4 滑窗 | v3ctl 滑窗 | 差值 |
  | --- | ---: | ---: | ---: |
  | Qwen3-ASR | 22.26 | 22.38 | −0.12（看起来持平） |
  | **GPT-ASR** | **24.14** | **18.53** | **+5.61（真实差距）** |

  机制：Qwen3-ASR 会把重复内容折叠掉，于是 v3ctl 滑窗里那些循环（8-gram
  重复率 0.070）在转写中被抹平，分数被人为抬高；GPT-ASR 逐字转写循环，
  循环该扣的分就扣掉了。
  **后果**：组 A（Qwen3-ASR）里所有**滑窗**数字都偏乐观，不可用于跨版本
  判断；reset 模式受影响较小（重复率本来就只有 0.013–0.016）。
  **规则更新**：凡涉及滑窗/退化音频的对比，一律用 GPT-ASR；Qwen3-ASR 仅
  用于 reset 模式的低成本回归。

### 6.4 v4 归因错误（假设部分成立）

- **错误**：预期"修好循环 → 滑窗 BLEU 上升"。
- **如何发现**：循环确实降了 5.4 倍（8-gram 重复率 0.070 → 0.013），
  但 BLEU 完全没动。
- **纠正后**：循环 ≠ 滑窗掉分主因。剩余约 6 分需另行定位。

### 6.5 脚本 bug：sliding6 静默产出空音频

- **错误**：`score_generic.py` 里 `rows_suffix = "swrow" if mode == "sliding"`
  用了精确匹配，`sliding6` 落到 `rows` 分支，去读 34 行的 session 文件对
  1 行的整场输出，row_id 全不匹配 → 拼接出 0 秒音频 → SEGALE 报空张量。
- **如何发现**：SEGALE 抛 `torch.cat(): expected a non-empty list`，回查
  日志见 `missing_rows: 34`。
- **纠正后**：改为 `mode.startswith("sliding")`，重跑得 19.90。
- **教训**：拼接环节缺少"missing_rows > 0 就报错"的断言，属于静默失败。
